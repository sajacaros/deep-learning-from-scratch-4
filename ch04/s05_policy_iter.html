policy_iter()의 여덟 줄을 그대로 옮겼습니다. 두 국면이 번갈아 돕니다.

평가 V(s) ← Σa π(a|s) { r + γV(s′) } 를 Δ < 0.001 이 될 때까지
개선 π(s) ← argmaxa { r + γV(s′) } [식 4.8]

  • 처음 정책은 네 방향 각각 0.25인 무작위 정책이라 칸마다 ↑↓←→가 함께 뜹니다. 한 번 개선하고 나면 화살표가 하나씩만 남습니다. 그림 4-16의 왼쪽에서 오른쪽으로 가는 과정입니다.
  • 칸 하나씩 끊어 보며 제자리 갱신이 스윕 안에서 어떻게 앞서 나가는지 확인하려면 s04_policy_eval.html 쪽이 낫습니다. 거기에는 배열 두 개(4.1.2)와 견줘보는 토글도 있습니다.
  • V를 사이클마다 새로 만들지 않고 이어 씁니다. 그래서 γ = 0.9 에서 첫 평가는 23 스윕이 걸리지만 두 번째부터는 4, 2, 2, 1 스윕이면 끝납니다. Δ 그래프에서 주황 파선 직후 선이 위로 튀었다가 금세 다시 임계값 아래로 떨어지는 모양으로 보입니다.
  • 멈추는 조건은 개선해도 정책이 그대로일 때(new_pi == pi)입니다. 값이 수렴한 것만으로는 멈추지 않습니다 — 마지막에 한 번 더 개선해 보고 바뀌는 칸이 없어야 끝납니다. γ = 0.9 에서는 사이클 5회입니다.
  • 개선에서 방금 방향이 바뀐 칸은 주황 테두리로 표시됩니다. 아래쪽 줄이 왼쪽으로 한 칸씩 차례로 바뀌는데, 한 사이클에 한 걸음씩 정보가 번져 나가는 모습입니다.
  • 최댓값이 동점인 칸은 s05_policy_iter.py의 argmax()와 똑같이 행동 번호가 가장 큰 쪽(↑ < ↓ < ← < →)을 고릅니다. 마지막에 나온 키를 고르는 그 구현입니다. γ를 0으로 두면 거의 모든 칸이 동점이 되어 화살표가 죄다 →로 몰리는데, 이 규칙이 눈에 보이는 순간입니다.
  • Δ가 정확히 0이 되는 스윕은 로그 눈금에 그릴 수 없어 그래프 바닥에 붙습니다. 결정적 정책에서는 두어 스윕 만에 값이 딱 맞아떨어져 실제로 자주 일어납니다.
  • 벽 칸은 갱신하지 않습니다. 파이썬 코드는 벽 칸의 값과 정책도 계산하지만 어떤 상태도 그 값을 읽지 않아 결과에 영향이 없습니다(README 4.4.2의 0.81 이야기).
  • γ를 바꾸면 처음(V = 0, 무작위 정책)부터 다시 시작합니다. 이 환경에서는 γ가 0보다 크기만 하면 최적 정책이 언제나 같습니다 — 달라지는 것은 값의 크기와 첫 평가에 걸리는 스윕 수뿐입니다 (첫 평가가 γ = 0.99 에서는 74 스윕, γ = 0.5 에서는 6 스윕. 이어지는 사이클은 어느 쪽이든 몇 스윕이면 끝납니다). 정확히 γ = 0 일 때만 한 걸음 앞의 보상밖에 못 봐 정책이 무너집니다.
